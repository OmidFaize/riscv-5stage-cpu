# RV32I 5-Stage Pipelined CPU

A 32-bit RISC-V processor implementing a subset of the RV32I base integer ISA,
written in SystemVerilog. This processor consists of a classic five-stage pipeline 
with full data forwarding, load-use interlock, and branch/jump flush logic.

Simulation only - verified in Vivado 2025.2 (XSim), Icarus Verilog, and cocotb.

---

## Overview

The core is a five-stage pipeline (IF / ID / EX / MEM / WB) with a Harvard memory
model and synchronous active-high reset. Branch and jump instructions resolve in EX, giving a
two-cycle penalty on a redirect, with implicit predict-not-taken behaviour.

**29 instructions implemented:**

| Class | Instructions |
|---|---|
| R-type | `add` `sub` `sll` `slt` `sltu` `xor` `srl` `sra` `or` `and` |
| I-type arithmetic | `addi` `slti` `sltiu` `xori` `ori` `andi` `slli` `srli` `srai` |
| Load / Store | `lw` `sw` |
| Branch | `beq` `bne` `blt` `bge` `bltu` `bgeu` |
| Jump | `jal` `jalr` |

---

## Features

- **Full data forwarding** — EX/MEM → EX and MEM/WB → EX, on both ALU operands
- **Load-use interlock** — one-cycle stall in ID, resolved through the existing
  MEM/WB forwarding path
- **Branch and jump flush** — taken branches and jumps flush both IF/ID and ID/EX
- **Register file write bypass** — a WB write is visible to a same-cycle ID read
- **17 self-checking testbenches, 124 assertions** — 4 integration benches covering
  all three hazard classes, plus 13 unit benches
- **Constrained-random cocotb verification** — Python golden model, hazard-biased
  program generation, live write-back scoreboard, and final data-memory comparison
- **Reproducible random testing** — deterministic seeds, readable assembly dumps on
  failure, and cycle/instruction diagnostics for mismatches
- **Mutation-validated** — RTL faults were deliberately injected to confirm that the
  directed and constrained-random tests detect real failures
- **Parameterised test programs** — each SystemVerilog testbench selects its own
  program, so no source edit is needed to switch tests

```
│   ├── pc.sv                       program counter

│   ├── if_id_reg.sv                IF/ID pipeline register

│   ├── id_ex_reg.sv                ID/EX pipeline register
│   ├── alu.sv                      ALU
│   ├── alu_control.sv              ALU operation decoder
│   ├── branch_target_adder.sv      pc + imm
│   ├── ex_mem_reg.sv               EX/MEM pipeline register
│   ├── dmem.sv                     data memory
│   ├── mem_wb_reg.sv               MEM/WB pipeline register
│   ├── wb_mux.sv                   writeback source select
│   ├── forwarding_unit.sv          data hazard detection
│   └── hazard_detection_unit.sv    load-use stall detection
└── sim_1/new/                      testbenches (17) and test programs
    ├── tb_core_top.sv              full integration, all hazard classes (28 checks)
    ├── tb_forwarding.sv            data forwarding (3 checks)
    ├── tb_branch.sv                all six branch types (15 checks)
    ├── tb_jump.sv                  jal / jalr (21 checks)
    ├── tb_*.sv                      13 unit benches (57 checks)
    ├── program_*.hex               test programs
    └── dmem_init.hex               data memory initialisation
```

`sim_build/` is generated by the cocotb runner. `generated/` is created when an
assembly listing is requested or when a random test fails. Both are ignored by Git.

## Running it

Get a copy of the project:

```bash
git clone https://github.com/OmidFaize/riscv-5stage-cpu.git
cd riscv-5stage-cpu
```

### Vivado

Open `riscv_5stage_cpu.xpr`. In the Sources panel, set the testbench you want as the
simulation top, then run **Run Simulation → Run Behavioral Simulation**. Results print
to the Tcl console.

### Icarus Verilog

Requires Icarus Verilog 12.0 or later. Run from the testbench directory, since
`$readmemh` resolves the `.hex` filenames relative to the working directory:

```bash
cd riscv_5stage_cpu.srcs/sim_1/new
iverilog -g2012 -o sim.vvp ../../sources_1/new/*.sv tb_core_top.sv
vvp sim.vvp
```

Substitute any other testbench name for `tb_core_top.sv`.

Icarus prints an informational note about constant selects in `always_*` blocks. It
does not affect results.

### Python / cocotb constrained-random verification

The Python verification flow runs separately from the 17 SystemVerilog testbenches:

```
random RV32I program → Python golden model → cocotb → SystemVerilog CPU
                                            ↓
                              live write-back scoreboard
                                            ↓
                                final data-memory check
```

`rv_model.py` implements the same 29 supported instructions and generates legal,
forward-only random programs. Source registers are biased toward recent destinations
so RAW dependencies and forwarding paths occur frequently instead of relying on pure
random chance.

`test_cpu.py` contains a small directed smoke test plus the constrained-random test.
cocotb drives the clock/reset and writes instruction and data memories directly through
VPI, allowing many programs to run in one simulator launch. Register write-backs are
compared against the Python model as they retire, then all 256 data-memory words are
checked after the pipeline drains.

`run_cocotb.py` builds the RTL with Icarus, starts the cocotb tests, passes the random
test settings, and returns a non-zero exit code if either cocotb test fails.

#### Setup

Requires Python 3, cocotb, and Icarus Verilog on `PATH`.

Create and activate a virtual environment, then install cocotb:

```bash
python -m venv .venv
```

Windows PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
pip install cocotb
iverilog -V
```

Linux / macOS:

```bash
source .venv/bin/activate
pip install cocotb
iverilog -V
```

If Icarus was installed through MSYS2 UCRT64 on Windows and is not found, add its
binary directory to the current PowerShell session:

```powershell
$env:Path = "C:\msys64\ucrt64\bin;$env:Path"
```

After opening a new terminal, reactivate `.venv` before running the Python tests.
The PATH command above also has to be repeated unless the Icarus directory was added
to the Windows User `Path` permanently.

#### Run the golden-model self-check

This checks the Python reference model by itself, without starting an HDL simulator:

```bash
python rv_model.py
```

A successful run ends with:

```
golden model self-check PASSED
```

#### Run the cocotb tests

Default run — 20 random programs with up to 60 generated body instructions each:

```bash
python run_cocotb.py
```

Longer stress test:

```bash
python run_cocotb.py --programs 300 --length 80
```

Useful options:

```bash
python run_cocotb.py --programs 200        # number of random programs
python run_cocotb.py --length 100          # generated body length per program
python run_cocotb.py --seed 12345          # deterministic base seed
python run_cocotb.py --waves               # generate a waveform dump
python run_cocotb.py --dump-seed 12345     # write one program as assembly only
```

`--seed` controls the random sequence, so rerunning the same command with the same
arguments reproduces the same set of generated programs. A failing random test also
writes `generated/seed_<N>.asm.txt`, showing the encoded word, disassembly, execution
order, and the instruction associated with the mismatch.

### Expected output

The directed SystemVerilog integration test ends with output similar to:

```
PASS: x1 = 100
PASS: x2 = 7
...
PASS: x28 (beq target) = 280
ALL TESTS PASSED
```

A successful cocotb stress test ends with lines similar to:

```
PASS - 300 programs, <instruction count> instructions, 0 mismatches
PASS - 2 cocotb test(s) passed
```

On Windows PowerShell, the runner's exit status can also be checked with:

```powershell
echo $LASTEXITCODE
```

`0` means the full cocotb run passed; a non-zero value means at least one test failed.
